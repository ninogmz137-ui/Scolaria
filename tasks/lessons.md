[2026-04-18] | FloatingTabBar rendered on top of a modal screen (Réglages) and on top of in-screen sidebar drawer (Aria) — `<Modal>` and in-Stack `transparentModal` both render BELOW the tab bar because the tab bar is owned by the parent Tab.Navigator. | For screens that must cover the floating tab bar (full-screen modals, sidebars), add a route-based opt-out in `FloatingTabBar.tsx`: `const ROUTES_HIDE_TAB_BAR = new Set([...]); if (ROUTES_HIDE_TAB_BAR.has(nestedRouteName)) return null;`. [2026-04-18] | `ChildPopover` in `FloatingTabBar.tsx` wrote three `sharedValue.value = withTiming(...)` **directly in the component render body** (pattern: `if (visible) { opacity.value = ...; ... } else { ... }`). Under the New Architecture (Fabric), this throws `[Reanimated] Writing to value during component render` on every render. Because `FloatingTabBar` re-renders on every tab press and route change, the warning multiplied to 60+ per navigation — and produced stale-frame rendering artifacts (ghost blocks, misplaced overlays on sibling screens). | Never mutate `sharedValue.value` in a component's body. The only safe places to write to a sharedValue are: (1) inside `useEffect` keyed on the relevant state, (2) inside event handlers (`onPress`, `PanResponder.onPanResponderMove`, etc.), (3) inside `runOnUI` callbacks. Pattern fix: wrap the whole `if (visible) { ... } else { ... }` block in `useEffect(() => { ... }, [visible, ...sharedValues])`. Under Fabric / strict mode this is not just a warning — it's a correctness bug that can cascade.
